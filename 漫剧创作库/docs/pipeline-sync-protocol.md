# 流水线链路闭环协议 — Pipeline Sync Protocol (v2 分层版)

> **核心原则**：每新增/修改一个 Skill、方法论、规范或 Agent 能力，必须执行链路闭环验证。  
> **但验证深度按影响等级分层**——不是每个变更都配得上全链路干跑，把 token 用在刀刃上。

---

## 一、影响等级分类（快速判断，< 100 tokens）

在执行闭环前，Producer 先用以下矩阵判断本次变更的影响等级：

| 等级 | 判断标准 | 典型场景 | 预估 token 消耗 |
|------|---------|---------|---------------|
| **L1 轻量** | 不改变产出格式、不改变 Agent 职责、不改变门禁条件、不改变数据流方向 | 修正 Skill 错别字/措辞、补充示例、优化说明文字、新增注释 | ~300 |
| **L2 中等** | 新增可选能力、补充但不替换已有规范、Agent 小幅调整、新增辅助文档 | 新增辅助类 Skill、补充方法论文档、Agent 增加可选职责、新增参考文档 | ~800 |
| **L3 重大** | 改变产出格式、改变 Agent 核心职责、改变门禁条件、新增/删除 Agent、接入新模型/工具、变更模板 | 修改核心 Skill 的输出格式、新增/删除 Agent、接入新模型、改项目模板、修改规范硬指标 | ~3000+ |

### 快速判断口诀

```
L1 = 只改了"怎么说"，没改"做什么"和"产出什么"
L2 = 新增了能力/文档，但不影响已有的流程和格式
L3 = 改了"产出什么"或"谁负责什么"或"怎么判断通过"
```

**拿不准时，默认 L2。** 宁可多查一步，不可漏掉关键传播。

---

## 二、L1 轻量闭环（3 步，~300 tokens）

适用于：措辞优化、错别字修正、示例补充、注释完善。

### Step 1：变更登记
```
- 等级：L1
- 变更：[文件名] — [一句话]
- 影响自评：不改变产出格式 / 不改变 Agent 职责 / 不改变门禁
```

### Step 2：传播自检（只做脑内检查，不读文件）
- [ ] 确认：本次变更不影响任何其他文件的输入/输出格式
- [ ] 确认：本次变更不涉及 workflow.md / phase-gate / Agent 定义中的硬性条目

### Step 3：日志签收
写入 `docs/pipeline-sync-log.md`，标记 L1，即完成。

> **L1 不读文件、不干跑、不传播。** 完全靠 Producer 的判断力兜底。

---

## 三、L2 中等闭环（4 步，~800 tokens）

适用于：新增可选 Skill、补充方法论、Agent 小幅调整、新增参考文档。

### Step 1：变更登记
```
- 等级：L2
- 变更：[文件名] — [一句话]
- 直接依赖方：[列出 1-hop 受影响文件]
```

### Step 2：上游依赖（只读被依赖文件，不全量扫描）
- [ ] 新 Skill 引用的 docs 是否存在
- [ ] 新规范引用的术语是否有对应（快速 grep，不全量读）
- [ ] 新 Agent 依赖的数据文件是否可用

### Step 3：直接下游传播（只更新 1-hop 节点）
| 检查项 | 动作 |
|--------|------|
| `workflow.md` Agent×Skill 总表 | 如新增 Skill，追加到对应 Agent 行 |
| 被引用的 Skill / Agent 定义 | 如新增文档被某 Skill 前置引用，在引用列表追加 |
| `docs/` 中的索引/目录 | 如新增方法论文档，更新相关 README 的目录 |

> **L2 不做端到端干跑。** 只确保直接上下游不断裂。

### Step 4：日志签收
写入 `docs/pipeline-sync-log.md`，标记 L2，列出传播的文件。

---

## 四、L3 重大闭环（6 步，完整验证）

适用于：改变产出格式、Agent 核心职责、门禁条件、新增/删除 Agent、接入新模型/工具、变更模板。

### Step 1：变更登记
```
- 等级：L3
- 变更：[文件名] — [一句话]
- 影响 Phase：Phase X → Phase Y
- 影响 Agent：Agent A, Agent B
- 影响范围预估：[详细说明]
```

### Step 2：上游溯源（全量检查依赖）
- [ ] 新变更的所有输入依赖是否就位
- [ ] 依赖的 docs / 数据文件 / API 文档是否可用且内容匹配

### Step 3：下游传播（全阶段扫描）
| 检查维度 | 具体动作 |
|---------|---------|
| `workflow.md` | 流程步骤表 + Agent×Skill 调用关系表是否需要更新 |
| Agent 定义 | 受影响 Agent 的 `agent.md` 是否需更新职责/输入/输出/Skill 列表 |
| Phase Gate | `phase-gate-checklist.md` 是否需新增检查项 |
| Skill 交叉引用 | 其他 Skill 的"前置读取"列表是否需加入新文档 |
| 项目模板 | `templates/` 中模板是否需同步更新 |
| 质量检查 | `quality-control-skill` / `script-review-skill` 审核维度是否需扩展 |

### Step 4：端到端干跑
选定一个**典型场景**（推荐用当前活跃项目），从变更点上游走到下游，验证：
- [ ] 新规范/Skill 在对应阶段的执行流程中是否被正确引用
- [ ] 产出的中间产物是否符合新规范要求
- [ ] 下一阶段的输入是否能正常接收上一个阶段的新格式产出
- [ ] 质检环节是否能检测到新规范的合规要求

### Step 5：回写同步
更新所有受影响文件（同原协议 Step 5）。

### Step 6：闭环签收
```
✅ 链路闭环签收 (L3)
- 变更名称：[名称]
- 验证日期：[YYYY-MM-DD]
- 干跑场景：[项目名 + 阶段范围]
- 上游依赖：[全部就位 / 缺失项清单]
- 下游传播：[已同步的文件列表]
- 端到端结果：[通过 / 存在风险（说明）]
- 签收人：Producer
```

## 五、批量窗口机制（省 token 的关键）

### 核心规则

| 等级 | 处理时机 | 批量规则 |
|------|---------|---------|
| **L1** | Phase Gate 切换时统一处理 | 可积累多个 L1，一次性日志签收 |
| **L2** | 下一个 Phase Gate 前，或积累 ≥ 3 个时 | 同类变更可合并传播检查 |
| **L3** | **立即执行，不可延迟** | 不参与批量，必须独立闭环 |

### 批量日志格式

当多个 L1/L2 一起签收时：
```markdown
## [YYYY-MM-DD] 批量签收 (Phase Gate: X → Y)

| # | 等级 | 变更 | 状态 |
|---|------|------|------|
| 1 | L1 | director-skill 措辞优化 | ✅ |
| 2 | L2 | 新增 action-case-opposition-force-camera.md | ✅ |
| 3 | L1 | 修正 shortdrama-script-standard.md 标题格式示例 | ✅ |
```

### 去重规则
- 如果同一文件在积累期间被多次修改，**只需对最终版本做一次闭环**
- 日志中记录最终版本即可，不记录中间过程

## 六、与 Phase Gate 的集成（精简版）

```
新变更发生
  ├─ L3 → 立即闭环 → Phase Gate 前确认签收
  ├─ L2 → 积累，Phase Gate 前批量闭环
  └─ L1 → 积累，Phase Gate 时顺便签收
       ↓
Phase Gate 正常门禁检查 → 放行
```

Producer 在 Phase Gate 前只需确认：
- [ ] 无未完成的 L3 闭环
- [ ] L1/L2 积累变更已在本次门禁前批量签收
- [ ] `docs/pipeline-sync-log.md` 无未签收的 L3 记录

---

## 七、常见反模式

| 反模式 | 正确做法 |
|--------|---------|
| 所有变更都走 L3 全链路干跑 | 用 L1/L2/L3 分级，~80% 的变更应该是 L1-L2 |
| L1 变更也读一堆文件验证 | L1 靠 Producer 判断力，不读文件 |
| L3 变更降级为 L2 跳过干跑 | 涉及产出格式/Agent职责/门禁的必须 L3 |
| L2 批量积累太多不处理 | ≥ 3 个 L2 或 Phase Gate 前必须清理 |
| 批量签收时不检查文件最终版本 | 批量签收前必须对最终版本做一次检查 |

## 八、快速执行清单

```
Pipeline Sync — [变更名称]

□ Step 0: 等级判断 → L1 / L2 / L3

--- L1 路径 ---
□ 登记变更 + 影响自评
□ 确认不影响产出格式/Agent职责/门禁
□ 写入日志（可批量）

--- L2 路径 ---
□ 登记变更 + 列出直接依赖方
□ 上游依赖快速检查
□ 直接下游传播（1-hop 更新）
□ 写入日志（可批量）

--- L3 路径 ---
□ 完整变更登记
□ 上游溯源（全量）
□ 下游传播（全阶段）
□ 端到端干跑
□ 回写同步
□ 闭环签收，写入日志（不可批量）
```
