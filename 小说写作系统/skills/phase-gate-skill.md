# phase-gate-skill — 阶段门禁技能

## 用途
在各阶段流转前执行统一门禁检查，配合 Producer 的放行判断。

## 触发条件
当一个阶段的工作完成，需要判断是否可以进入下一阶段时调用。

## 输入
- 当前阶段的所有产出文件
- `docs/phase-gate-checklist.md`

## 输出
- 门禁检查结果（放行/小修放行/打回）
- 阻塞点说明
- 必改项清单

---

## 方法论

### 一、门禁检查流程

```
1. 确认当前阶段
2. 加载对应阶段的检查清单
3. 逐项检查
4. 汇总结果
5. 输出判定
```

### 二、检查清单（按阶段）

详见 `quality-control-skill` 中的阶段门禁检查部分。

### 三、判定规则

| 结果 | 条件 | Producer 动作 |
|------|------|--------------|
| 放行 | 所有必查项通过 | 下发下一阶段任务 |
| 小修放行 | 有小问题但不影响核心 | 标注问题，允许带问题进入下一阶段 |
| 打回 | 有核心问题 | 退回当前阶段，下发返工指令 |

### 四、门禁报告格式

```markdown
## 门禁检查报告

- 项目：[项目名]
- 当前阶段：Phase [X]
- 检查日期：YYYY-MM-DD

### 检查结果
[逐项列出]

### 判定：放行 / 小修放行 / 打回
### 阻塞点：[如有]
### 必改项：[如有]
```

### 五、特殊规则

1. Phase 1 → Phase 2 的门禁最严格：故事核不清晰绝不放行
2. Phase 3 可以分批放行（每 5 章一次门禁）
3. Phase 5 的门禁必须由 Reviewer 和 Producer 双重确认

### 六、闭环验收检查思路（样板项目专用）

对于用于验证系统流程的样板项目，需要额外执行闭环验收检查：

**结构闭环检查**：
- 仓库 README 声明的模块是否全部落盘？
- `docs/workflow.md` 的阶段划分是否与项目目录一致？
- 模板文件是否与实际项目需求匹配？
- 是否存在"文档说有但实际没有"的文件？

**执行闭环检查**：
- 每个阶段是否有明确的输入→输出→门禁？
- 门禁清单是否真正可执行（不是空话）？
- Agent 职责是否清晰无重叠？
- Skill 是否能指导真实操作？

**内容闭环检查**：
- 样板项目是否完成了真实内容填充？
- 是否只是骨架而没有实质验证？
- 发现的问题是否已回写到系统文档？

**验收产出**：
- 样板项目需产出 `09-retro/closure-audit.md`
- 发现的缺口需立即回写到 `docs/workspace-status.md`
- 可复用资产需回写到 `docs/`、`skills/`、`templates/`
